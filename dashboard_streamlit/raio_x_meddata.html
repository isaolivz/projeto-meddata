Challenge Oracle 2026 · Relatório de projeto

Raio-X do MedData

Um painel de monitoramento de ocupação hospitalar do SUS (São Paulo) com IA generativa como interface de consulta. Este documento registra, com números reais, o que o MVP entrega, os bugs que encontramos e corrigimos ao longo do desenvolvimento, e as limitações que decidimos documentar em vez de esconder.

Streamlit Oracle ADB Select AI / Cohere LangChain + ChromaDB Pandas / Plotly
01

O que o MVP entrega

Cinco frentes, cada uma com um propósito só: mostrar volume, mostrar risco, responder pergunta direta, conversar com recomendação, e explorar previsão de curto prazo.

Página
Visão Geral
Volume de internações, diagnósticos (CID), distribuição geográfica e evolução mensal — contexto, não risco.
Página
Monitoramento
Alertas críticos, ranking de risco por hospital e ocupação agregada da rede — o núcleo da tese do projeto.
Página
Pergunte aos Dados
Perguntas diretas em português, respondidas via Select AI contra o schema real do Oracle ADB.
Página
Chat MedData
Mesmo motor, com roteamento por IA e uma base de conhecimento (RAG) que orienta recomendações.
Protótipo
Novo design visual
Linguagem visual editorial (paleta restrita, linhas finas) testada lado a lado com o design atual, sem risco para o app principal.
Exploração
Painel preditivo
Notebook com forecast de curto prazo (Holt-Winters), validado com MAPE — ainda não integrado ao app.

03

Bugs reais, encontrados e corrigidos

Cada um destes foi reproduzido com uma consulta real contra o banco antes de ser considerado corrigido — nenhuma correção foi assumida sem reteste.

Leitos ~11,5× inflados na tabela de hospitais Corrigido na origem
A coluna leitos_totais da versão atualizada dos dados tinha um problema de geração. Corrigido via UPDATE direto na tabela, usando o valor real da geração anterior (casado pelo código CNES), para 1.404 dos 1.466 hospitais.
média V2: 926,9 leitosdevia ser80,8 leitos (média V1, real)
total em São Paulo: 1.358.903→39.848 leitos, após a correção
Persona do agente confundindo a geração de SQL Corrigido
O parágrafo de contexto do agente ("Você é um agente de Capacidade...") entrava no mesmo texto da pergunta usado para gerar SQL. Corrigido separando os dois: a pergunta vai pura para a geração de SQL, o contexto só entra na explicação final.
"Quantas internações ocorreram no total?" sozinha: 671.860 (correto)
mesma pergunta com o parágrafo de contexto na frente: 10.048.284 (somou dias de internação, não contou internações)
IA tentando usar funções que não existem no Oracle Mitigado via RAG
Para calcular distância entre coordenadas, o modelo gerava SQL com PI() e SDO_GEOM.SDO_DISTANCE — nenhuma das duas existe neste banco (não há metadado espacial cadastrado, e o Oracle não tem função PI()). Corrigido fornecendo uma fórmula pronta (lei dos cossenos esférica com RADIANS()) na base de conhecimento.
ORA-00904: "PI": invalid identifier — consulta inteira rejeitada
Mesma pergunta, número diferente — view errada Mitigado via RAG
Duas views de nome parecido cobrem períodos diferentes. Uma delas soma só os últimos 12 meses; a IA às vezes a escolhia para perguntas sobre o total histórico, sem avisar a limitação. Documentamos o escopo exato de cada view na base de conhecimento.
"total geral de internações": 671.860 (view sem filtro de tempo) vs. 632.233 (view de 12 meses, usada por engano)
Borda de extração de dados parecendo uma queda real Identificado e corrigido
Os últimos dias disponíveis na base têm contagem artificialmente baixa — a extração dos dados aconteceu no meio do processamento do último mês, não porque as internações caíram de verdade. Sem tratar isso, um modelo de previsão confunde com tendência de queda real e projeta valores negativos.
últimos dias: 1.031 → 739 → 326 → 63 internações/dia
erro do modelo de previsão (MAPE): 147,7%→22,4%, após excluir a borda
04

Limitações que decidimos documentar

Estas não têm correção definitiva com o que temos hoje — preferimos deixar explícito o limite a fingir que não existe.

Select AI é não-determinístico Conhecida
A mesma pergunta, feita duas vezes, pode gerar SQL diferente — e portanto resposta diferente. As correções acima reduzem a frequência disso, mas não eliminam: é uma característica do modelo, não um bug pontual.
Perguntas de distância continuam frágeis Conhecida
Mesmo com a fórmula certa disponível na base de conhecimento, o modelo às vezes ainda tenta SDO_GEOM de novo, ou usa uma coordenada de referência errada. É o ponto mais frágil do sistema hoje.
Respostas não sinalizam nível de confiança Conhecida
Uma resposta certa e uma resposta duvidosa saem com o mesmo tom de segurança — não há hoje um sinal visual de "isso é exato" vs. "isso é uma estimativa".
Índice composto de risco (MDS) adiado Bloqueado por dado externo
Depende de população por município (IBGE), que ainda não temos. Decidimos não implementar com um substituto improvisado — fica para quando o dado real chegar.
05

Próximos passos

Em ordem de prioridade — o primeiro item ataca diretamente a limitação mais séria da lista acima.

1
Separar entendimento de execução
Para perguntas conhecidas (ranking de risco, hospital mais próximo com vaga), usar uma consulta pronta e testada em vez de deixar a IA reescrever o SQL toda vez — elimina a classe inteira de bug de fórmula errada para esses casos.
2
Validar o painel preditivo com mais dado
O notebook já mostra MAPE de 22,4% num teste — rodar de novo conforme mais meses de dado ficarem disponíveis, antes de expor isso como página do dashboard.
3
Implementar o MDS com dado real de população
Assim que tivermos população por município (IBGE), retomar o índice composto que ficou pausado por falta desse dado.
